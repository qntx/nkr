## Summary

Measured on 2026-10-18 against strfry 1.1.3, nkr at commit 22be2f1.

nkr is ahead on:

- ingest throughput: 1.7x on the synthetic corpus, 3.1x on the real one;
- concurrent query throughput: roughly 1.5x to 3x in most scenarios;
- live delivery latency: about 10x lower median;
- tail latency of `OK`;
- live delivery under permessage-deflate. strfry falls seconds behind there, while nkr stays within hundreds of milliseconds.

nkr is behind on:

- single-query latency to `EOSE`: strfry is faster by roughly 10% to 40% on 500-event queries;
- time to the first event: strfry is 2x to 4x faster;
- memory per connection: 34x more when idle, 4.5x more with deflate;
- CPU per live delivery: about 1.6x to 2x more;
- the p99 of indexed live delivery.

These gaps are the work items in [Open gaps](#open-gaps). "Aligned with strfry" is not claimed until they close.

## Method

- **relayBench** (amethyst `relayBench`, commit 9847d0a) is a third-party harness. It replays a deterministic corpus over 4 publisher connections, then runs 12 client-shaped queries: 10 rounds on one connection, then 8 connections at once. It also cross-checks result sets; there were no mismatches in any run. NIP-77 sync was skipped (`--no-sync`) because nkr does not implement it yet.
- **nkrbench** (`bench/nkrbench` in this repository) measures what relayBench does not:
  - live fan-out latency for every subscriber and event pair, with exact delivery accounting (all runs: zero missing, zero duplicates);
  - anonymous resident memory per idle subscribed connection;
  - relay CPU seconds per scenario.

  Rates were chosen to stay below saturation of both relays and of the harness.

- **Fairness:**
  - both relays use LMDB with the same synchronous commit;
  - both verify signatures and run their stock defaults, with the same event size, tag, and age limits;
  - every scenario starts from a fresh database;
  - relay order rotates between repetitions. Within relayBench, strfry always runs first; that is a limitation of the harness.
- **Environment (primary):**
  - Linux aarch64 in an OrbStack VM on an Apple M5, with 10 vCPUs and a btrfs volume;
  - every relay is pinned to cores 0 to 3 and the harness to cores 4 to 9, so client and relay never compete for CPU;
  - relayBench ran 3 times on the synthetic corpus and 2 times on the real dump; nkrbench ran 3 repetitions;
  - values are medians, with min and max in brackets;
  - strfry is the pristine 1.1.3 tag built with its own Makefile (`-O3`, LTO).

strfry's live delivery waits on a 100 ms debounce of database change notifications, by design (`RelayReqMonitor`, `file_change_monitor`). That is the source of its latency floor and of part of its CPU saving: it batches about 10 events per wake-up at 100 events/s. strfry compresses on its single WebSocket thread, which saturates under deflate.

## Open gaps

1. **Time to first event and to EOSE.** Confirmed in code: a filter's matches are collected, sorted, and emitted only when its scan completes. The merge already produces descending `created_at` order, so each completed `created_at` group can be streamed as soon as the merge moves past it. Ordering and limit semantics stay unchanged.
2. **Memory per connection.** Measured, cause not yet profiled. The deflate share follows from default zlib state for both directions per connection (window 15, memory level 8). Next step: a heap profile of an idle connection, followed by sizing the read buffer, the deflate memory level and window, and the per-connection allocations.
3. **CPU per live delivery.** Hypothesis: one task wake-up and one write syscall per event per subscriber, against strfry's batched writes. Next step: a CPU profile of the broadcast scenario.
4. **p99 of indexed live delivery and of `OK`.** Unexplained. Next step: instrument writer commit times and runtime stalls under the selective scenario.

## Secondary run on macOS

The same suites also ran natively on macOS 27. The results agree on the direction of ingest throughput (2x to 3.4x) and concurrent query throughput, but they are not used for conclusions:

- LMDB on Apple platforms commits with `F_FULLFSYNC`, which dominates write latency for both relays;
- `ps` resident memory is not reliable there;
- the first broadcast scenarios were run above saturation, so the client and the relay competed for the same cores.

During that run, strfry master (4cd3cf6) crashed with a `phmap` assertion. Its new `ReadRestrictor` lazily initializes a shared static set from all ingester threads without synchronization. The 1.1.3 release does not contain that code.
