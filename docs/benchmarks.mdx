## Summary

The current results come from round 4 (PR #3), measured against strfry 1.1.3 and the previous `main` in one side-by-side run.

nkr is ahead on:

- ingest throughput: 1.7x on the synthetic corpus, 2.1x on the real one;
- time to `EOSE` on 500-event queries: 10% to 40% faster;
- time to first event: at parity or faster;
- concurrent query throughput: about 3x;
- live delivery latency: 6x to 16x lower median;
- live delivery under permessage-deflate: strfry falls seconds behind, nkr stays at 14 ms median;
- storage: about 3% smaller.

nkr is behind on:

- memory per idle connection: 18x without deflate, 1.8x with it;
- CPU per live broadcast delivery: about 2.2x;
- `OK` latency on the synthetic corpus: 2.68 against 2.16 ms at the median, a deliberate durability difference (see [Durability](#durability)).

## Method

- **relayBench** (amethyst `relayBench`, commit 9847d0a) is a third-party harness. It replays a deterministic corpus over 4 publisher connections, then runs 12 client-shaped queries: 10 rounds on one connection, then 8 connections at once. Its OkHttp client negotiates permessage-deflate. It cross-checks result sets; there were no mismatches in any run. NIP-77 sync is skipped (`--no-sync`) until nkr implements it.
- **nkrbench** (`bench/nkrbench`) measures:
  - live fan-out latency for every subscriber and event pair, with exact delivery accounting;
  - anonymous resident memory per idle subscribed connection;
  - relay CPU seconds per scenario.

  Rates are chosen to stay below saturation of both relays and of the harness.

- **Fairness:**
  - both relays use LMDB and verify signatures;
  - both run stock defaults with the same event size, tag, and age limits;
  - every scenario starts from a fresh database;
  - relay order rotates between repetitions. Within relayBench, strfry always runs first; that is a limitation of the harness.
- **Environment:**
  - Linux aarch64 in an OrbStack VM on an Apple M5, with 10 vCPUs and a btrfs volume;
  - every relay is pinned to cores 0 to 3 and the harness to cores 4 to 9;
  - relayBench ran 3 times on the synthetic corpus (100,000 events) and 2 times on the real 2024 dump (29,016 events); nkrbench ran 3 repetitions;
  - values are medians;
  - strfry is the pristine 1.1.3 tag built with its own Makefile (`-O3`, LTO).
- **Variance:** absolute numbers move by up to 2x between sessions on this VM, for every relay alike, and p99 values vary widely within a session. Only comparisons within one run are used. The round 4 session ran slow overall: strfry ingested 4,320 events/s here against 7,723 events/s in round 3.

## Durability

strfry opens its LMDB environment through rasgueadb with `MDB_CREATE`. `MDB_CREATE` is a database flag. Its value, 0x40000, is the same bit as the environment flag `MDB_NOMETASYNC`, so in `mdb_env_open` strfry effectively runs with `MDB_NOMETASYNC`. Evidence:

- the flags returned by `mdb_env_get_flags` after such an open;
- strace of 200 sequential commits: strfry writes the meta page through the plain file descriptor in about 20 µs, while nkr writes it through LMDB's synchronous descriptor in about 1.2 ms.

The data `fdatasync` costs the same for both relays.

According to LMDB's documentation, `MDB_NOMETASYNC` preserves integrity but "a system crash may undo the last committed transaction". strfry can therefore acknowledge an event that a power loss then rolls back. nkr keeps LMDB's default and syncs the meta page before `OK`.

In round 3, a measurement-only build of nkr with `MDB_NOMETASYNC` acknowledged in 1.04 ms against strfry's 1.28 ms (synthetic) and 1.42 ms (real). The remaining median `OK` gap is this durability difference.

strfry's live delivery waits on a 100 ms debounce of database change notifications, by design (`RelayReqMonitor`, `file_change_monitor`). That debounce is its latency floor. It is also part of its CPU saving, because about 10 events are batched per wake-up at 100 events/s. strfry compresses on its single WebSocket thread, which saturates under deflate.

p99 values in this session varied between repetitions by up to 5x for every relay. In round 3, under quieter conditions, nkr's p99 for selective delivery was 8 ms against strfry's 102 ms.

## Changes by round

- **Round 1:**
  - TCP_NODELAY on accepted sockets;
  - batched outbound flushes and bounded socket writes;
  - a shutdown deadline;
  - O(1) live-index removal.
- **Round 2:** one live iterator per scan cursor and constant-memory deduplication. Scan micro-benchmarks run 48% to 59% faster.
- **Round 3:**
  - results are streamed per `created_at` group and pushed to connections in chunks, with the first frame of each scan sent alone;
  - one write deadline per batch;
  - the system allocator instead of mimalloc: memory per connection fell from 34.8 to 20.9 KiB idle and from 493 to 220 KiB with deflate, with no throughput loss.
- **Round 4:**
  - **Compression:** deflate level 1, as in strfry's uWS. Level 6 had dominated large responses to deflate clients. `EOSE` on 500-event queries fell by about 55% against the previous build, for example firehose from 14.18 to 6.02 ms.
  - **`REQ` path:** the shard forwards scans and cancels to the reader, so a `REQ` crosses two threads instead of three.
  - **`OK` path:** the writer pushes `OK` frames straight onto the connection's queue, which removes one task wake-up per `OK`.
  - **Memory:** dropping the per-connection reply futures cut idle memory from 20.8 to 18.0 KiB and deflate memory from 220 to 192 KiB.
- **Measurements rejected:**
  - streaming without chunking lowered 8-connection throughput by 11% to 25%;
  - the zlib-rs deflate backend used more memory than the default backend.

## Open gaps

1. **Memory per connection.** About 15 KiB of the 18 KiB idle footprint is yawc's socket read and write buffers. With deflate, the default backend also allocates compressor and decompressor state eagerly for every connection. Closing this gap needs smaller or lazily allocated buffers in yawc itself. It is tracked as an upstream change rather than a fork.
2. **CPU per live delivery.** nkr writes each event to each subscriber as it commits: one wake-up and one write per delivery. strfry batches about 10 events per write behind its 100 ms debounce. The extra CPU is the price of the latency difference above. It shrinks as load rises, because a connection drains everything queued into one write.

## Secondary run on macOS

The same suites also ran natively on macOS 27. The results agree on the direction of ingest and concurrent query throughput, but they are not used for conclusions:

- LMDB on Apple platforms commits with `F_FULLFSYNC`, which dominates write latency for both relays;
- `ps` resident memory is not reliable there.

During that run, strfry master (4cd3cf6) crashed with a `phmap` assertion. Its new `ReadRestrictor` lazily initializes a shared static set from all ingester threads without synchronization. The 1.1.3 release does not contain that code.
