## Summary

Measured on 2026-10-18 against strfry 1.1.3, nkr at commit 2b1c208. All figures come from runs in which every relay in a table ran side by side.

nkr is ahead on:

- ingest throughput: 1.4x on the synthetic corpus, 2.1x on the real one;
- concurrent query throughput: about 2.5x;
- live delivery latency: 7x to 15x lower median, with tighter p99;
- live delivery under permessage-deflate: strfry falls almost a second behind, nkr stays at 7 ms;
- storage: about 4% smaller.

nkr is at parity on small lookups (profiles, threads, ids, conversations).

nkr is behind on:

- time to `EOSE` for 500-event queries: strfry is about 10% to 25% faster;
- time to first event: bimodal, sometimes at strfry's 0.1 ms and sometimes 0.5 ms;
- memory per idle connection: 21x without deflate, 2x with it;
- CPU per live delivery: about 2.5x.

nkr acknowledges events about 0.6 ms later than strfry at the median. The cause is identified and deliberate; see [Durability](#durability).

"Aligned with strfry" is not claimed while these gaps remain open.

## Method

- **relayBench** (amethyst `relayBench`, commit 9847d0a) is a third-party harness. It replays a deterministic corpus over 4 publisher connections, then runs 12 client-shaped queries: 10 rounds on one connection, then 8 connections at once. It cross-checks result sets; there were no mismatches in any run. NIP-77 sync is skipped (`--no-sync`) until nkr implements it.
- **nkrbench** (`bench/nkrbench`) measures:
  - live fan-out latency for every subscriber and event pair, with exact delivery accounting (every run: zero missing, zero duplicates);
  - anonymous resident memory per idle subscribed connection;
  - relay CPU seconds per scenario.

  Rates are chosen to stay below saturation of both relays and of the harness.

- **Fairness:**
  - both relays use LMDB and verify signatures;
  - both run stock defaults with the same event size, tag, and age limits;
  - every scenario starts from a fresh database;
  - relay order rotates between repetitions. Within relayBench, strfry always runs first; that is a limitation of the harness.
- **Environment:**
  - Linux aarch64 in an OrbStack VM on an Apple M5, with 10 vCPUs and a btrfs volume;
  - every relay is pinned to cores 0 to 3 and the harness to cores 4 to 9;
  - relayBench ran 3 times on the synthetic corpus (100,000 events) and 2 times on the real 2024 dump (29,016 events); nkrbench ran 3 repetitions;
  - values are medians, with min and max in brackets;
  - strfry is the pristine 1.1.3 tag built with its own Makefile (`-O3`, LTO).
- **Variance:** absolute numbers move by up to 2x between sessions on this VM, for both relays alike. Only comparisons within one run are used; every table below comes from a single run.

## Durability

strfry opens its LMDB environment through rasgueadb with `MDB_CREATE`. `MDB_CREATE` is a database flag. Its value, 0x40000, is the same bit as the environment flag `MDB_NOMETASYNC`, so in `mdb_env_open` strfry effectively runs with `MDB_NOMETASYNC`. Evidence:

- the flags returned by `mdb_env_get_flags` after such an open;
- strace of 200 sequential commits: strfry writes the meta page through the plain file descriptor in about 20 µs, while nkr writes it through LMDB's synchronous descriptor in about 1.2 ms.

The data `fdatasync` costs the same for both relays, about 1.4 ms on this disk.

According to LMDB's documentation, `MDB_NOMETASYNC` preserves integrity but "a system crash may undo the last committed transaction". strfry can therefore acknowledge an event that a power loss then rolls back. nkr keeps LMDB's default and syncs the meta page before `OK`. A measurement-only build of nkr with `MDB_NOMETASYNC` acknowledges in 1.04 ms (synthetic) and 1.04 ms (real), ahead of strfry. The remaining `OK` gap is this durability difference and nothing else.

strfry's live delivery waits on a 100 ms debounce of database change notifications, by design (`RelayReqMonitor`, `file_change_monitor`). That debounce is its latency floor. It is also part of its CPU saving, because about 10 events are batched per wake-up at 100 events/s. strfry compresses on its single WebSocket thread, which saturates under deflate. In the deflate row strfry used less CPU because it was saturated and fell behind; nkr kept up.

## Changes since the first round

All measured in the same run against the previous build:

- **Scan:** one live iterator per cursor instead of a seek per key, and constant-memory deduplication. Scan micro-benchmarks run 48% to 59% faster.
- **Streaming:** each completed `created_at` group is emitted as soon as the merge passes it. The reader pushes results to the connection in chunks, and the first frame of a scan goes out alone. The first frame's emit inside the scan dropped from 121 µs to 3 µs.
- **Writes:** one write deadline per batch instead of a timer per frame. Clock reads had taken about 6.6% of fan-out CPU.
- **Allocator:** the system allocator replaces mimalloc. Memory per connection fell from 34.8 to 20.9 KiB idle and from 493 to 220 KiB with deflate, with no throughput loss.
- **Measurements rejected:**
  - streaming without chunking lowered 8-connection throughput by 11% to 25% and was replaced by the chunked design;
  - the zlib-rs deflate backend used more memory than the default backend (377 against 220 KiB per connection).

## Open gaps

1. **Time to `EOSE` on large results.** Every event is copied twice on the way out: once into a frame `String` in the reader, and once into the WebSocket write buffer. strfry writes from the memory map into its socket buffers on one thread.
2. **Bimodal time to first event.** The same build measures 0.1 ms or 0.5 ms across runs, for both the nkr build and its measurement variant. The likely cause is wake-up latency across the three thread hops (connection, shard, reader) on idle vCPUs. This is not yet proven.
3. **Memory per connection.** About 15 KiB per idle connection are the WebSocket read and write buffers. The rest is the connection task, its channel, and its session. Under deflate, the default backend allocates compressor and decompressor state eagerly for every connection.
4. **CPU per live delivery.** One wake-up and one write per event per subscriber, against strfry's 100 ms batching. Strace shows 0.39 `sendto` calls per delivery.

## Secondary run on macOS

The same suites also ran natively on macOS 27. The results agree on the direction of ingest and concurrent query throughput, but they are not used for conclusions:

- LMDB on Apple platforms commits with `F_FULLFSYNC`, which dominates write latency for both relays;
- `ps` resident memory is not reliable there;
- the first broadcast scenarios were run above saturation.

During that run, strfry master (4cd3cf6) crashed with a `phmap` assertion. Its new `ReadRestrictor` lazily initializes a shared static set from all ingester threads without synchronization. The 1.1.3 release does not contain that code.
