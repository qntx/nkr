---
title: 0002 Sans-IO core
description: Why the protocol core emits commands instead of calling a storage trait, and how that serves both runtimes.
---

## Context

nkr runs on tokio with blocking LMDB threads natively, and inside a single-threaded Durable Object with synchronous SQLite in wasm. A shared asynchronous storage trait would force async overhead onto synchronous LMDB reads. It would also run into `Send` bounds that wasm types do not satisfy, and it would hide the very different concurrency models behind one abstraction.

## Decision

The `nkr` crate is sans-IO: no async, no I/O, no clock, and no randomness. A session consumes frames and emits a command stream: publish, subscribe, unsubscribe, and send. Each runtime decides where and how each command executes. The pure semantic rules (kind classes, replaceable ordering, and in layer 2 deletion and expiration rules) are functions in the core that both stores call inside their own transactions.

This is the pattern used by quinn-proto, rustls, and h2-sans-io.

## Alternatives

- **One async store trait shared by both runtimes.** Rejected for the reasons above.
- **One ordered key-value engine running on both LMDB and SQLite.** Rejected in [ADR 0006](/decisions/0006-durable-object-sqlite): it would cross the wasm boundary once per cursor step and pay per-row billing for index emulation.

## Consequences

- Every protocol decision is testable deterministically without sockets or databases.
- CI compiles the core for `wasm32-unknown-unknown` on every commit, so native-only code cannot leak in.
- The two stores implement their own query execution. A shared differential test suite keeps them equivalent ([Testing](/testing)).
