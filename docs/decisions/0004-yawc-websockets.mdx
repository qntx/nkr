---
title: 0004 yawc WebSockets
description: Why the native server uses yawc for WebSockets, with axum for HTTP routing.
---

## Context

strfry negotiates permessage-deflate, optionally with a sliding window, and nostr traffic compresses well: repeated subscription ids, pubkeys, and event ids. A relay without compression spends noticeably more bandwidth than strfry for the same work.

## Decision

Use yawc for WebSockets, through its axum integration, with axum serving the HTTP surface (upgrade, NIP-11, metrics). yawc implements RFC 6455 and RFC 7692. It passes the Autobahn suite in client and server modes, supports context-takeover control (strfry's sliding-window switch), and is actively maintained.

## Alternatives

- **tungstenite and tokio-tungstenite.** As of 0.29 they still do not support permessage-deflate.
- **fastwebsockets.** Fast, but has no compression support.
- **uWebSockets through FFI.** This is strfry's choice. It would bring a C++ build and unsafe glue into an otherwise safe Rust server.

## Consequences

- Per-connection memory depends on the compression mode. Sliding-window mode keeps a deflate context per connection and per direction, and it is configurable exactly as in strfry.
- The WebSocket layer's conformance is covered by yawc's Autobahn runs. nkr's end-to-end tests cover only protocol behavior.
