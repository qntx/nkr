## Engine

LMDB through heed: one environment with several named databases. Reads come straight from the page cache with no locks and no system calls, and they scale with cores. There is exactly one writer. [ADR 0003](/decisions/0003-lmdb-via-heed) covers the choice.

Environment defaults:

- map size 10 TiB (virtual address space, not disk usage);
- 256 maximum readers;
- read-ahead enabled, with a switch to disable it for databases larger than RAM;
- read transactions opened without thread-local storage, so a transaction can be handed to a reader thread.

## Sequence numbers

Every stored event gets a sequence number `seq: u64` from a persistent counter in the `meta` database. The counter is advanced inside the write transaction and is never reused, even after deletions. Sequence numbers are the primary key, they define insertion order, and they are the boundary between a subscription's historical scan and its live stream.

## Databases

All integers in keys are big endian, so byte order equals numeric order. No custom comparators are needed.

| Database         | Key                                            | Value                                                     |
| ---------------- | ---------------------------------------------- | --------------------------------------------------------- |
| `meta`           | name                                           | format version, next seq, later the negentropy tree roots |
| `events`         | seq                                            | packed record                                             |
| `payloads`       | seq                                            | canonical JSON                                            |
| `ix_id`          | id                                             | seq                                                       |
| `ix_time`        | created_at, seq                                | id                                                        |
| `ix_pubkey`      | pubkey, created_at, seq                        | empty                                                     |
| `ix_kind`        | kind (2 bytes), created_at, seq                | empty                                                     |
| `ix_pubkey_kind` | pubkey, kind, created_at, seq                  | empty                                                     |
| `ix_tag`         | tag name, value length, value, created_at, seq | empty                                                     |
| `ix_replace`     | address hash                                   | seq                                                       |

The address hash is the SHA-256 of kind, pubkey, and `d` value. It is computed for replaceable kinds (with an empty `d`) and for addressable kinds (with the full first `d` value, even when it is too long to index). Every index except `ix_id` and `ix_replace` ends with `created_at` and `seq`, so a time-bounded scan is a contiguous key range.

Layer 2 adds `ix_deletion` (NIP-09 targets by id and author), `ix_replace_deletion` (NIP-09 address deletions by address hash and `created_at`), `ix_expiration` (NIP-40), and the persistent negentropy tree.

## Write path

A single writer thread owns every write transaction.

1. Block on the queue for the first request, then drain without blocking until the queue is empty or the batch cap is reached (1024 events by default).
2. Open one write transaction. Apply each event in arrival order:
   - **Duplicate** (`ix_id` hit): accepted, with `duplicate: have this event`.
   - **Replaceable or addressable**: look up `ix_replace`. If the stored version wins under the NIP-01 rule (newer `created_at`; on a tie, the lower id), reject with `duplicate: have a newer version`. Otherwise delete the old event and every index entry it owns, then insert the new one.
   - **Insert**: take the next seq, then write `events`, `payloads`, and every index key.
3. Commit with fsync.
4. Answer every request in the batch, then broadcast the committed batch (events and their seq) to the monitor shards.

Ephemeral events never reach the writer. Batching amortizes the fsync across concurrent publishers, which is what lets durable writes keep up under load.

## Read path

### Planning

Each filter is planned independently, using exactly one index:

1. impossible filter: skipped;
2. `ids`: point lookups in `ix_id`;
3. `authors` with `kinds`: `ix_pubkey_kind`, one cursor per (author, kind) pair while the pair count stays under a cap, otherwise `authors` alone;
4. `authors`: `ix_pubkey`;
5. tag filters: `ix_tag` on the tag key with the fewest values;
6. `kinds`: `ix_kind`;
7. otherwise: `ix_time`.

Each cursor scans backward over the key range bounded by `until` and `since`. Cursors are merged by `created_at` with a binary heap. Every candidate's packed record is loaded from `events` and checked with the core matcher. The scan stops when the effective limit is reached. All further candidates that share the boundary `created_at` are then collected, sorted by id ascending, and truncated, so ties follow the NIP-01 order. Results are deduplicated by seq across the filters of one request.

### Snapshot and exactly-once delivery

The snapshot S of a scan is assigned by the subscription's monitor shard: it is the highest seq that shard has already received from the writer. The shard handles registration and committed batches in one ordered inbox. Every batch above S therefore reaches the shard after the subscription exists, and every seq up to S is already committed and visible to readers. Every slice skips keys whose seq is above S; seq is the last component of every index key, so the check is cheap. The live monitor delivers only seq above S. A scan may span several transactions, but no event is delivered twice and none is missed.

### Time slicing

A scan runs for a budget of 10 ms by default. At the end of a slice it saves the last key of each cursor, drops its iterators, and ends its read transaction. A long-lived read transaction would stop LMDB from reusing freed pages and make the file grow without bound. Resumption opens a fresh transaction and continues each cursor just after its saved key.

Each reader thread keeps a queue: new scans always run before resumed ones, so short queries are never stuck behind long ones. A scan also pauses when its connection's outbound buffer is above the high-water mark, and resumes once it drains.

## Durability and format

- An `OK` is sent only after the commit that contains the event has returned. The environment uses LMDB's default fully synchronous commit: data pages are synced, then the meta page. `MDB_NOMETASYNC` is deliberately not used. It would save one sync per commit, but a system crash could undo the last acknowledged transaction, which strfry effectively accepts ([Benchmarks](/benchmarks#durability)).
- The format version is stored in `meta`. A binary that finds a different version refuses to open the database. Upgrades go through `nkr export` and `nkr import`. There is no in-place migration code.
