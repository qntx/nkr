## System shape

```text
                 ┌──────────────── nkr (sans-IO protocol core) ────────────────┐
                 │ event · packed · filter · message · session · monitor ·      │
                 │ limits · kind semantics · (layer 2: nip42 · nip45 · nip77)   │
                 └──────────────┬───────────────────────────────┬───────────────┘
                                │                               │
       nkr-lmdb (LMDB store, query engine, writer)     nkr-sql (SQL store logic)      layer 3
                                │                               │
       nkr-server (binary `nkr`: tokio, axum + yawc,   nkr-worker (workers-rs,         layer 3
                   threads, CLI, config, metrics)        Durable Object adapter)
```

| Crate        | Target                           | Published         | Role                                                                                                                                                   |
| ------------ | -------------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `nkr`        | native, `wasm32-unknown-unknown` | yes               | Protocol core: validation, canonical encoding, filters, messages, per-connection session, live-subscription index                                      |
| `nkr-lmdb`   | native                           | yes               | LMDB schema, writer with group commit, pausable query engine                                                                                           |
| `nkr-server` | native                           | no (binary `nkr`) | Network runtime, thread topology, CLI, configuration, metrics                                                                                          |
| `nkr-sql`    | native, wasm                     | no                | SQL schema, query compilation, and write transactions over a minimal executor. It runs on Durable Object SQLite in production and on rusqlite in tests |
| `nkr-worker` | wasm                             | no                | Cloudflare Worker entry and Durable Object adapter                                                                                                     |

Crates are added only when the layer that needs them starts. There are no placeholder crates.

## Invariants

These rules hold everywhere. A change that breaks one needs a new decision record first.

1. **The core is sans-IO.** `nkr` has no async runtime, no I/O, no clock, and no randomness. Time and challenges are passed in. It compiles to `wasm32-unknown-unknown` in CI on every commit.
2. **Protocol decisions live only in the core.** Runtimes parse nothing and validate nothing themselves. They execute the commands that a session emits and feed results back.
3. **LMDB is touched only by dedicated threads.** The single writer thread and the reader pool own every transaction. Async workers never touch the memory map, because a page fault on a cold page would stall the reactor.
4. **Serialize once.** An event is serialized to canonical JSON once, at ingest. Every later delivery inserts those stored bytes into the frame verbatim.
5. **Exactly-once delivery across history and live.** A subscription's historical scan returns only events with sequence number up to its snapshot S. The live stream delivers only events with sequence number above S. See [Storage](/architecture/storage).
6. **The connection is the final gate.** Every outbound `EVENT` and `EOSE` carries its subscription generation. The connection task drops frames for generations that are no longer current, which settles every race between `CLOSE` and in-flight results.
7. **Everything is bounded.** Ingest queues, the writer queue, outbound bytes per connection, scan time slices, subscriptions per connection, filters per request, and negentropy session memory all have limits.

## EVENT flow (native)

1. The connection task receives a text frame and calls the session's `on_text`.
2. The session parses and checks structure and limits, then checks the time window. Only then does it hash and verify the signature. Cheap rejections happen before the expensive work.
3. The session emits a publish command carrying the verified event, shared behind a reference count.
4. Ephemeral kinds go straight to the monitor shards. All other kinds go to the writer queue.
5. The writer drains its queue, applies each event inside one LMDB write transaction, and commits with fsync. It then answers every waiting connection with its outcome and broadcasts the committed batch, tagged with sequence numbers, to every monitor shard.
6. The connection sends `OK`. The `OK` never precedes a durable commit.

## REQ flow (native)

1. The session validates the request and emits a subscribe command with a fresh generation.
2. The connection registers the subscription with its monitor shard as pending. The shard replies with snapshot S, the highest seq it has already received from the writer.
3. A reader thread runs the historical scan in time slices of 10 ms by default. It skips sequence numbers above S and streams results to the connection.
4. When every filter's scan completes, the connection sends `EOSE`. The shard flushes the live matches it buffered while the scan ran, all with sequence above S, and moves the subscription to active.
5. From then on, every committed batch is matched against the shard's inverted index, and one shared copy of each event's JSON is fanned out to all matching subscriptions.
